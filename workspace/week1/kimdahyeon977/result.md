## 검증과 증거

- 모든 10개 실행은 `turn/end`의 `completed`로 종료했다.
- JSON 두 결과는 코드 울타리 제거 후 같은 객체로 파싱되며, Minimal 원문은 그대로 파싱된다.
- Python 두 함수는 코드 블록 추출 후 빈 입력, 중복, 음수, 순서 보존 사례에서 같은 정답을 반환했다.
- 정규식 두 결과는 ASCII 정상/오류 문자열을 대상으로 확인했다. Python의 `$`는 마지막 개행 앞에서도 매칭될 수 있어, 엄격한 검증에는 fullmatch 등 엔진의 전체 매칭 기능을 함께 사용한다.
- 실제 답변과 지표는 세션 기록에서 추출했다. 이번 제출에는 이 보고서만 포함하며 인증 정보와 원시 세션 로그는 포함하지 않았다.

## 원인 분석 — 구성 차이가 결과에 어떻게 연결되는가?

### 1. Standard와 Minimal의 실제 차이

두 모드는 동일한 모델을 사용했지만, 모델에 전달하는 시스템 지침과 도구 구성이 달랐다. 프리셋 설정 파일뿐 아니라 실제 요청 직전에 기록된 `system/message`와 `request/header`도 확인했다.

| 항목 | Standard | Minimal |
|---|---|---|
| 첫 모델 요청의 시스템 지침 길이 | 6,865자 | 46자 |
| 모델에 제공된 도구 수 | 27개 | 1개: bash |
| 시스템 지침 구성 | 코딩 에이전트 역할, 작업 위치, 도구 사용 안내 등 여러 섹션 | `You are a helpful software engineer assistant.` |
| 런타임 컨텍스트 | 기본 설정에서 제공 | `includeRuntimeContext: false`로 억제 |
| 추가 시스템 지침 합성 | 여러 플러그인의 섹션을 합성 | `complete: true`로 다른 섹션과 suffix 억제 |
| Skill 지원 | 탐색·로딩 도구 제공 | Skill 도구 없음 |

Standard의 도구에는 파일 읽기·편집·쓰기·검색, 웹 검색·조회, Skill, 계획, 목표, 하위 에이전트, 워크플로 등이 포함됐다. 도구의 **제공**과 **호출**은 다르다. JSON과 Python 실험에서는 Standard가 이 도구들을 실제로 호출하지 않았다. 따라서 “Standard가 Skill을 실행해서 답변이 나빠졌다”는 설명은 이번 기록으로 뒷받침되지 않는다.

구성 확인 근거:

- Standard 설정: 로컬 Harness의 `packages/preset/agent-presets/presets/standard/agent.cordis.yml`.
- Minimal 설정: 로컬 Harness의 `packages/preset/agent-presets/presets/minimal/agent.cordis.yml`.
- 로컬 Harness의 `packages/preset/persona/src/index.ts`: complete 설정과 런타임 컨텍스트 억제가 실제로 적용되는 코드.
- 실제 요청 기록의 시스템 지침 문자 수, 도구 목록, 실행 단계 시각을 확인했으며 주요 수치는 아래 표에 포함했다. 별도 증거 파일은 이번 제출에 포함하지 않았다.

### 2. 입력 토큰이 크게 줄어든 이유 — 구성과 측정이 뒷받침하는 설명

모델은 사용자가 입력한 질문뿐 아니라 시스템 지침과 사용할 수 있는 도구의 설명·매개변수도 입력으로 받는다. 이번 질문은 짧았지만 Standard에는 길고 다양한 추가 정보가 전달됐다. Minimal은 짧은 지침과 도구 하나만 전달해, 작업에 필요한 입력 외의 부담이 작았다.

JSON 과제의 입력은 Standard 9,446토큰, Minimal 820토큰이었다. 전체 토큰도 9,468에서 841로 약 91.1% 감소했다. Python은 약 90.8%, 정규식은 약 80.7% 감소했다. 이는 해당 실행의 전체 처리 토큰 비교이며 비용 감소율을 뜻하지 않는다.

Standard의 JSON usage에는 일반 입력 3토큰 외에 캐시 읽기 8,697토큰과 캐시 쓰기 746토큰이 기록됐다. 따라서 일반 입력 3토큰만 보고 Standard의 입력이 더 작다고 판단하면 잘못된 비교가 된다. 보고서의 입력에는 이 세 항목을 모두 더했다.

이번 기록은 지침·도구 구성의 총합이 큰 입력량 차이를 만들었다는 설명을 뒷받침한다. 다만 문자 수는 토큰 수와 같지 않으며, 각 플러그인이 차지한 토큰을 따로 계산하지 않았으므로 구성 요소별 기여율은 알 수 없다.

### 3. Minimal이 출력 형식을 더 잘 지킨 이유 — 가능한 해석과 미확인 부분

확인된 현상은 Standard가 JSON과 정규식에 코드 블록을 붙이고 Python에 소개 문장을 추가한 반면, Minimal은 JSON·정규식을 한 줄로 출력하고 Python의 소개 문장을 생략했다는 것이다. 내용의 정확성보다 **사용자가 요구한 형식 준수**에서 차이가 났다.

가능한 해석은 Standard의 여러 코딩·도구 사용 지침과 모델의 일반적인 코드 답변 방식이 함께 작용하면서, 사용자가 요청한 최소 출력보다 설명·서식이 추가됐다는 것이다. Minimal에는 부가 지침이 적어 해당 실행에서 질문의 출력 조건을 더 직접적으로 따른 것으로 볼 수 있다.

그러나 이것은 원인 가설이다. 실제 입력에서 모든 코드 답변을 코드 블록으로 감싸라고 강제하는 지침을 확인하지 못했다. 또한 동일 조건 반복 실행과 지침별 제거 실험을 하지 않았으므로, “지침이 많아서 형식 준수 능력이 떨어진다”거나 “특정 Skill이 코드 블록을 만들었다”고 확정할 수 없다. 모델 출력의 변동성도 대안 설명으로 남는다.

세 사례의 판단 강도도 다르다. JSON은 “코드 블록 없이”를 명시했으므로 명확한 조건 준수 차이다. 정규식은 “한 줄만”이라는 조건에서 차이가 있다. Python은 두 답변 모두 코드 울타리를 포함했고 소개 문장 유무만 달라, 개선 폭이 작은 사례다.

### 4. 정규식에서 Minimal이 더 느렸던 이유 — 추가 모델 단계가 생겼다

Minimal은 최종 답변 전에 `bash`로 정규식을 echo했다. 이는 실제 입력 문자열에 대한 정규식 검증이 아니라 텍스트 출력이며, 이 과제를 해결하는 데 필요하지 않았다.

| Minimal 실행 구간 | 턴 시작 기준 시각 |
|---|---:|
| 첫 모델 단계 시작 | 0.024초 |
| bash 호출 기록 | 2.102초 |
| bash 결과 기록 | 2.815초 |
| 두 번째 모델 단계 시작 | 2.825초 |
| 두 번째 모델 단계 종료 | 14.069초 |
| 턴 종료 | 14.071초 |

bash 호출부터 결과까지는 약 0.713초였다. 반면 두 번째 모델 단계는 약 11.244초였다. 따라서 14초를 전부 Shell 실행 시간으로 설명하면 부정확하다. 도구 호출로 추가 모델 단계가 생겼고, 해당 단계의 응답 대기·생성 시간이 큰 부분을 차지했다. 그 내부 시간을 네트워크 지연과 모델 처리 시간으로 더 분리할 수 있는 자료는 없다.

Minimal의 정규식 실행은 모델 단계 2개, Standard는 1개였다. Minimal의 1,736 입력 토큰과 88 출력 토큰은 두 모델 응답의 합계다. 최종 정규식은 짧지만 도구 호출과 후속 응답 때문에 처리량이 추가됐다. 이는 도구 수가 적어도 불필요한 도구 사용까지 없어지는 것은 아니라는 사례다.

### 5. 이번 실험에서 확인하지 못한 원인

각 과제에서 Standard를 먼저, Minimal을 나중에 실행했다. 실행 순서를 교차하지 않았으므로 시간 차이를 Harness 구성만의 효과로 볼 수 없다. 같은 모델 경로를 사용했지만, 생성 설정 전체를 별도로 고정·대조한 실험은 아니다. 새 세션이라도 공급자 측 프롬프트 캐시는 공유될 수 있다.

또한 Skill 개수만 바꾼 것이 아니라 프롬프트, 도구, 컨텍스트 제공 방식이 함께 바뀌었다. 따라서 이 실험의 직접적인 비교 대상은 **두 프리셋 전체 구성**이다. Skill의 독립적인 효과를 측정한 실험은 아니다.

원인을 더 확실하게 확인하려면 같은 질문을 여러 번 실행하며 순서를 교차하고, Standard에서 도구 설명만 줄인 조건, 부가 지침만 줄인 조건, Skill 기능만 제거한 조건을 따로 비교해야 한다. 반복 실행에서는 JSON 원문 파싱 가능 여부, 한 줄 출력 여부, 불필요한 문장 유무를 같은 기준으로 집계할 수 있다. 이러한 후속 실험은 이번 보고서에는 수행하지 않았다.

## 종합 결론

이번 실험에서 Minimal은 JSON 변환, Python 함수 출력, 정규식 출력에서 불필요한 서식이나 소개 문장을 덜 추가했다. 그중 JSON은 명시된 출력 조건 준수에서 가장 분명한 개선을 보였고, Python은 구현의 우열 없이 표현의 간결성에서 작은 개선을 보였다. 세 과제 모두 전체 처리 토큰은 줄었지만 정규식은 더 느렸다.

구성과 실제 요청 기록을 보면 Minimal의 짧은 시스템 지침과 단일 도구가 입력 토큰 감소를 설명한다. 반면 답변 형식 개선의 정확한 원인은 반복·분리 실험 없이 확정할 수 없다. 이번 과제의 결론은 **“도구와 지침이 많은 구성이 모든 작업에서 더 좋은 것은 아니며, 간단하고 출력 조건이 명확한 작업에서는 Minimal이 더 적합한 결과를 낼 수 있다”**이다.
