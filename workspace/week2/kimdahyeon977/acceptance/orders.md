# Order, inventory, and payment CLI contract

Build a dependency-free Node.js ESM CLI at `cli.mjs`, with cohesive modules under `lib/`. Every invocation is a fresh process. `ORDER_FILE` selects a JSON store; separate paths are independent. A successful command prints exactly one JSON value and exits zero. Errors exit nonzero and leave the store's bytes unchanged. Read-only commands on a missing store return empty data without creating a file. No network services or real payments are involved.

Use these commands and exact result shapes:

- `product add SKU STOCK PRICE` returns `{sku,stock,reserved:0,price}`. `product list` returns products in creation order with current `stock` and `reserved`. `stock` is physical units and `reserved` is units held for unpaid orders. Available units equal `stock-reserved`.
- `order create ID SKU QTY` reserves available units and returns `{id,sku,qty,total,status:"reserved",payment:null}`, where `total=qty*price` in cents at order creation. `order get ID` returns one order; `order list` returns orders in creation order.
- `order pay ID KEY approved|declined` records a simulated payment attempt. A declined attempt keeps the order reserved and returns the order with `payment:{key,status:"declined"}`. A later attempt with a new key may approve. An approved attempt sets `status:"paid"`, `payment:{key,status:"approved"}`, subtracts `qty` from both product `stock` and `reserved`, and returns the order. There is no charge outside the store.
- Payment keys are globally unique. Repeating the same `order pay` command with the same key, order, and outcome returns **the original response** and changes no store bytes, even if the order has since changed. Reusing a key with another order or outcome is an error. A new payment key on a paid, cancelled, or refunded order is an error.
- `order cancel ID` on a reserved order releases its reservation and returns the order with `status:"cancelled"` and its latest payment field. On a paid order it restores `qty` physical units and returns the order with `status:"refunded"` and its approved payment field. Repeating cancellation of a cancelled or refunded order returns the current order without changing store bytes.
- `audit` returns an ordered array of `{seq,type,id}`. Each successful state-changing command appends exactly one event with consecutive `seq` starting at 1. Event types are `product.add`, `order.create`, `payment.declined`, `payment.approved`, `order.cancelled`, and `payment.refunded`; `id` is the product SKU for `product.add` and the order ID for the other types. Duplicate payment-key requests, repeated cancellation, reads, and errors append no event.

Identifiers `SKU`, `ID`, and `KEY` match `^[A-Z][A-Z0-9-]{0,15}$`. `STOCK` is a canonical decimal integer from 0 to 1,000,000; `PRICE` is canonical 1 to 1,000,000,000 cents; `QTY` is canonical positive decimal without a leading zero and must fit available stock. Canonical numbers have no sign, leading zeros, exponent, decimal point, or whitespace. `total` must be a safe integer. Duplicate products or orders, unknown entities, insufficient stock, extra or missing arguments, and invalid commands are errors.

Persist one JSON document with top-level `{version:1,events:[...]}`. Reconstruct current state, used payment keys, and audit results from committed events when a new process starts. Event objects may contain additional data needed for replay. A corrupted or inconsistent store must cause a nonzero exit without overwriting it. Commit a complete replacement atomically so a failed command cannot leave a partial event. `ORDER_FAILPOINT=before_commit` simulates an interruption after validation but before commit: every state-changing command under this setting fails, leaves existing store bytes unchanged (or absent store absent), and can be retried normally after clearing the setting. Reads and idempotent no-op commands remain successful under this setting.

Suggested implementation milestones: storage and product rules; reservation and order reads; payment attempts and idempotency; cancellation and refund; event replay, atomic failure behavior, and regression checks. These are milestones for organizing work, not prescribed round boundaries. The complete contract applies from the start. Concurrent writers, externally modified valid logs, and physical disk failure during rename are outside the contract.
