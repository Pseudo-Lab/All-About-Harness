- 작성자: y00njaekim

- 환경: macOS arm64, Node.js v24.19.0, DeepSeek Harness 0.1.5-rc.3, Web UI, dsh-codex-subscription 2.1.6

- 모델: 실험 1은 gpt-5.6-sol, 실험 2·3은 gpt-6.1-sol. 각 실험의 Minimal/Standard 쌍은 같은 모델을 사용했다.
- 작업 공간: 동일한 임시 작업 폴더. 파일 권한은 workspace-write, 승인 정책은 ask였다.

## 실험 설계와 집계 방법

사전 지식과 문제의 정의가 충돌하는 질문, 웹 검색을 요구하는 질문, 셸 상태를 사용하는 질문을 비교했다. 아래 본 실험은 각 mode의 새 세션에서 동일한 질문을 한 번씩 실행했으며, 추가 질문이나 힌트가 없는 완료된 세션만 사용했다. 모델 변경·중단·실패·여러 질문이 섞인 예비 시도는 본 비교에서 제외했다. 각 조건은 1회 측정이므로 반복 실험에 의한 재현성은 확인하지 않았다.

로컬 세션 로그의 `agent-preset/selected` 이벤트와 실제 요청의 모델 설정으로 mode와 모델을 확인했다. 세션 생성 당시 기본값만으로 mode를 판정하지 않았다. 실행 시간은 `turn/start`부터 `turn/end`까지의 차이로, 질문 접수 후 도구 실행과 최종 응답을 포함하는 서버 측 경과 시간이다. 브라우저 렌더링 시간은 포함하지 않는다.

토큰은 해당 turn의 모든 `assistant/message.usage`를 합산했다. 이 provider의 `inputTokens`는 비캐시 입력이며, 표의 입력 합계는 여기에 `cacheReadTokens`를 더한 값이다. 전체 토큰은 기록된 `totalTokens`를 합산했고 입력 합계+출력과 일치함을 확인했다. 제목 생성용 별도 요청은 제외했다. 토큰 수를 금전 비용으로 환산하지 않았다.

실제 요청에 전달된 함수 도구는 Minimal 2개(`bash`, `codex_image_generate`), Standard 28개였다. 설치한 구독 플러그인 때문에 Minimal도 Bash만 있는 구성은 아니었다. 이번 실험에서는 이미지 도구와 `skill` 로더를 호출하지 않았다. 따라서 관찰한 차이를 Skill 개수만의 효과로 분리할 수 없다.

## 실험 1 — 사전 지식과 다른 용어 정의

### 질문

```text
이 문제에서 ‘서버’는 요청을 보내는 쪽이고 ‘클라이언트’는 요청을 받는 쪽이다. A가 B에게 요청을 보냈다. 위 정의만 사용해서 A와 B의 역할을 한 줄로 답해줘
```

### 답변과 평가

- Minimal: “A는 서버이고, B는 클라이언트이다.”
- Standard: “A는 서버이고 B는 클라이언트다.”

둘 다 문제에서 지정한 정의를 따랐고, 일반적인 서버·클라이언트 용례에 끌려가지 않았다. 둘 다 도구를 호출하지 않았다. “Standard가 추가 문맥 때문에 사전 지식에 더 의존할 것”이라는 가설은 이 실행에서 지지되지 않았다.

Minimal의 전체 토큰은 768개로 Standard 8,134개보다 약 90.6% 적었고, 실행 시간도 1.568초로 2.049초보다 짧았다. Minimal의 장점은 동일한 정답을 더 적은 토큰으로 얻었다는 점이다. 답변 정확성 자체는 동률이다.

## 실험 2 — 웹 검색과 문제 내 정의의 충돌

### 질문

```text
이 문제에서 ‘서버’는 요청을 보내는 쪽이고 ‘클라이언트’는 요청을 받는 쪽이다. A가 B에게 요청을 보냈다. 웹 서치를 사용해서 A와 B의 역할을 한 줄로 답해줘
```

### 측정 결과

| 항목                   | Minimal             | Standard            |
| ---------------------- | ------------------- | ------------------- |
| 실행 시작 (KST)        | 2026-10-14 20:58:59 | 2026-10-14 20:58:46 |
| 모델                   | gpt-6.1-sol         | gpt-6.1-sol         |
| 사용 Tool              | bash                | web_search          |
| Tool 호출 횟수         | 1                   | 1                   |
| 모델 응답 횟수         | 2                   | 2                   |
| 입력 토큰 (캐시 포함)  | 1,779               | 16,840              |
| 입력 토큰 중 비캐시    | 1,779               | 8,904               |
| 입력 토큰 중 캐시 읽기 | 0                   | 7,936               |
| 출력 토큰              | 127                 | 94                  |
| 전체 토큰              | 1,906               | 16,934              |
| 전체 실행 시간         | 11.426초            | 11.675초            |

### 답변과 실제 검색 동작

- Minimal: “웹 검색의 일반적 용례와 무관하게, 이 문제의 정의에 따르면 A는 서버, B는 클라이언트입니다.”
- Standard: MDN 링크를 제시하고, 일반적인 용례와 달리 문제의 정의에서는 A가 서버, B가 클라이언트라고 답했다.

Standard는 `web_search`를 1회 호출했다. 검색어는 `MDN client server requests client sends server receives`였고, 결과에는 MDN의 요청·응답 설명이 포함되어 있었다.

Minimal은 전용 `web_search` 도구를 호출하지 않았다. 대신 `bash`에서 아래 명령을 실행했다.

```sh
curl -L --max-time 15 -s 'https://www.google.com/search?q=client+server+client+sends+request+server+receives' | head -c 500
```

반환된 것은 Google Search HTML의 앞 500바이트였다. 제목·스타일·스크립트·noscript 안내 부분으로, 서버와 클라이언트의 역할을 설명하는 검색 결과 본문은 확인되지 않았다. 따라서 Minimal이 검색 사이트에 접근한 사실은 확인되지만, 유효한 검색 근거를 얻어 답변에 활용했다고 보기는 어렵다. “Minimal도 web_search를 썼다”보다 “Minimal도 범용 Bash로 검색 페이지 접근을 시도했다”가 정확하다.

### 평가

최종 역할 판정은 둘 다 정답이다. Standard는 실제 검색 결과와 출처를 제공했으므로 검색 수행의 충실성은 Standard가 더 좋았다. Minimal은 전체 토큰을 약 88.7% 적게 사용했지만, 이것만으로 더 좋은 답변이라고 판정하지 않았다. 실행 시간은 Minimal 11.426초, Standard 11.675초로 차이가 작았다.

전용 검색 도구가 없어도 네트워크 접근이 가능한 범용 셸로 검색을 시도할 수 있었다. 도구 목록에 검색 도구가 없다는 사실과 검색 행동이 불가능하다는 것은 같지 않았다.

## 실험 3 — Bash 호출 사이의 상태 유지

### 질문

```text
셸의 상태가 다음 실행까지 유지되는지 확인해줘.

아래 명령을 순서대로 실행하되, 반드시 각각 별도의 Bash 도구 호출로 실행해줘.
명령을 합치거나, 변수를 다시 설정하거나, 파일로 상태를 전달하지 마.

1. export SKILL_TEST_VALUE=alpha
2. SKILL_TEST_VALUE="${SKILL_TEST_VALUE}-beta"
3. printf '[%s]\n' "$SKILL_TEST_VALUE"
```

### 측정 결과

| 항목                   | Minimal             | Standard            |
| ---------------------- | ------------------- | ------------------- |
| 실행 시작 (KST)        | 2026-10-14 21:03:10 | 2026-10-14 21:02:54 |
| 모델                   | gpt-6.1-sol         | gpt-6.1-sol         |
| 사용 Tool              | bash, bash, bash    | bash, bash, bash    |
| Tool 호출 횟수         | 3                   | 3                   |
| 모델 응답 횟수         | 4                   | 4                   |
| 입력 토큰 (캐시 포함)  | 3,462               | 32,948              |
| 입력 토큰 중 비캐시    | 3,462               | 16,820              |
| 입력 토큰 중 캐시 읽기 | 0                   | 16,128              |
| 출력 토큰              | 124                 | 155                 |
| 전체 토큰              | 3,586               | 33,103              |
| 전체 실행 시간         | 14.932초            | 13.527초            |

### 도구 출력과 답변

두 mode 모두 지시대로 별도의 Bash 호출을 3회 실행했다. 첫 두 명령에는 의미 있는 표준 출력이 없었고, 세 번째 명령의 출력이 달랐다.

| 항목                | Minimal                          | Standard                                   |
| ------------------- | -------------------------------- | ------------------------------------------ |
| 세 번째 명령의 출력 | `[alpha-beta]`                   | `[]`                                       |
| 최종 설명           | 변수 상태가 다음 실행까지 유지됨 | 셸 변수 상태가 다음 호출까지 유지되지 않음 |

Minimal의 Bash는 지속 셸이고 Standard의 Bash는 호출마다 새 셸을 실행한다. 이 차이는 실제 요청에 포함된 도구 설명과 실행 결과 모두에서 확인했다. 두 답변은 각각 관찰한 출력과 일치했다.

### 평가

Minimal은 상태를 이어 사용하는 작업을 직접 수행할 수 있었다. 그러나 질문은 “상태가 유지되는지 확인”하는 것이므로, 유지되지 않는다고 정확히 보고한 Standard도 정답이다. 이 결과를 모델의 추론 능력 차이나 Standard의 오답으로 해석하지 않았다.

Minimal의 전체 토큰은 3,586개로 Standard 33,103개보다 약 89.2% 적었다. 반면 실행 시간은 Minimal 14.932초, Standard 13.527초로 Minimal이 1.405초 더 길었다. 토큰 감소가 항상 시간 감소로 이어지지는 않았다. Standard의 입력에는 캐시 읽기 16,128개가 포함되지만, 한 번의 관찰로 시간 차이의 원인을 캐시라고 단정할 수는 없다.

## 종합 결론

세 질문에서 Minimal이 정확성으로 우세한 사례는 확인하지 못했다. 두 mode 모두 문제의 정의를 지켰고 셸 실험 결과도 정확히 설명했다. 웹 검색의 근거 확보는 Standard가 더 충실했다. 따라서 이 보고서는 “Minimal이 더 좋은 답변을 낸 질문 3개”를 찾았다는 성공 보고가 아니라, 해당 가설을 검증한 결과와 한계를 기록한 것이다.

Minimal은 세 실험 모두 전체 토큰이 약 89~91% 적었다. 단순한 정의 적용에는 추가 기능 없이도 같은 정답을 얻었지만, 도구가 적은 구성에서도 범용 셸로 외부 접근을 시도할 수 있었다. 또한 두 mode는 도구 개수뿐 아니라 시스템 지시문, Skill 카탈로그, 실행 문맥, 셸의 상태 유지 방식도 달랐다. 이번 결과만으로 Skill 개수와 품질 사이의 인과관계를 확정할 수 없다.

실행 순서는 세 쌍 모두 Standard 다음 Minimal이었다. 캐시, 네트워크, 서버 부하, 출력 길이의 영향을 통제하지 않았고 조건당 1회만 측정했다. 다음 실험에서는 순서를 번갈아 반복하고, 정답률·지시 준수·근거의 충실성과 토큰·시간을 각각 평가할 필요가 있다.
