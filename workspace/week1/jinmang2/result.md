# Week 1 — Skill은 많을수록 좋을까? (jinmang2)

- 실행 시각: 2026-10-13 10:48 (KST)
- 모델: `deepseek-v4-flash`, thinking 켬, reasoning effort high (두 mode 모두 같은 설정)
- 실행 방식: DeepSeek Harness `headless`로 질문마다 새 세션을 열어 한 번씩 실행
- 토큰: 입력은 캐시된 토큰까지 포함한 값이고, 전체는 입력과 출력을 더한 값
- 실행 시간: 에이전트가 턴을 시작해서 끝낼 때까지 걸린 시간(DSH Web의 "Ran for"와 같은 기준). headless 프로세스가 뜨고 내려가는 시간은 뺐다
- 채점: 정답이 하나로 정해진 질문은 정규식으로 확인했고, 답변 품질은 같은 모델로 LLM-judge 점수(5점 만점)를 매겼다

## 1. 실험 질문: 오늘 서울 날씨는 어땠어?

| 항목 | Minimal mode | Standard mode |
|---|---|---|
| 답변 요약 | 오전에 비가 집중됐고(8~9시 시간당 5~6mm) 오후부터 그친다. 현재 16.3°C, 최고 19.7°C, 총 강수량 약 20mm | 출근길에 가을비가 왔고 낮까지 5~20mm 더 내린다. 최고 21도, 오후부터 찬 바람이 불어 내일 아침 9도까지 떨어진다. 뉴스 출처 2개를 붙였다 |
| 사용 Tool | bash (wttr.in, Open-Meteo 조회) | bash, web_search, web_fetch (KBS, 연합뉴스 기사) |
| Tool 호출 수 | 3 | 4 |
| 입력 토큰 | 7,275 | 35,573 |
| 출력 토큰 | 2,035 | 923 |

두 mode 모두 실제로 날씨를 조회했다. Minimal은 웹 검색 도구가 없어서 bash로 날씨 API를 직접 불렀고, Standard는 검색해서 뉴스 기사를 읽었다.

결과는 예상과 달랐다. Standard가 토큰은 4배쯤 더 썼지만 오히려 5초 넘게 빨랐고, 내일 기온 같은 맥락과 출처까지 붙였다. Minimal은 wttr.in과 Open-Meteo 두 API를 차례로 불러 보느라 bash를 세 번 썼고, 출력 토큰도 그만큼 길어졌다. 최신 정보가 필요한 질문에서는 Standard의 도구가 제값을 했다.

## 2. Standard mode보다 Minimal mode가 더 잘 답한 질문 3개

세 질문 모두 두 mode의 정답은 같았다. 차이는 같은 답을 얻는 데 든 토큰에서 크게 났고, 시간은 요일 질문에서만 확실히 갈렸다.

### 질문 1. 2026년 12월 25일은 무슨 요일이야? 요일만 답해줘.

| 항목 | Minimal mode | Standard mode |
|---|---|---|
| 답변 요약 | 금요일 | 금요일 |
| 사용 Tool | 없음 | bash (`date -j -f ... "+%A"`) |
| Tool 호출 수 | 0 | 1 |
| 입력 토큰 | 481 | 14,804 |
| 출력 토큰 | 183 | 374 |
| 전체 토큰 | 664 | 15,178 |
| 실행 시간 | 1.5초 | 3.3초 |
| 정답 확인 | 통과 | 통과 |
| 품질 점수 (LLM-judge) | 5 | 5 |

**Minimal이 더 낫다고 본 이유**: 모델이 바로 계산할 수 있는 질문인데 Standard는 굳이 bash로 `date`를 실행했다. 도구를 한 번 부르면 모델을 한 번 더 호출해야 하고, 이때 시스템 프롬프트와 도구 설명이 통째로 다시 들어간다. 그래서 Standard는 토큰을 23배 쓰고 시간도 두 배 넘게 걸렸다. 도구가 많은 구성에서 필요 없는 도구 호출이 나온 사례다.

### 질문 2. 이 폴더(하위 폴더 제외)에 .txt 파일이 몇 개 있어? 숫자만 답해줘.

| 항목 | Minimal mode | Standard mode |
|---|---|---|
| 답변 요약 | 7 | 7 |
| 사용 Tool | bash (`find . -maxdepth 1 -type f -name '*.txt' \| wc -l`) | bash (같은 명령) |
| Tool 호출 수 | 1 | 1 |
| 입력 토큰 | 1,135 | 14,606 |
| 출력 토큰 | 179 | 177 |
| 전체 토큰 | 1,314 | 14,783 |
| 실행 시간 | 2.3초 | 2.5초 |
| 정답 확인 | 통과 | 통과 |
| 품질 점수 (LLM-judge) | 5 | 5 |

**Minimal이 더 낫다고 본 이유**: 도구가 꼭 필요한 질문이었고, 두 mode가 글자 하나 다르지 않은 명령을 실행해 같은 답을 냈다. 그런데 Standard의 입력 토큰은 13배였다. Minimal에 있는 도구는 bash 하나지만 이 작업에는 그걸로 충분했고, Standard가 더 가진 Skill과 도구 설명은 매 호출마다 실려 가는 비용으로만 남았다.

### 질문 3. 1부터 100까지 정수 중에서 3의 배수이면서 5의 배수가 아닌 수의 합은? 숫자로 답해줘.

| 항목 | Minimal mode | Standard mode |
|---|---|---|
| 답변 요약 | 1368 | 1368 |
| 사용 Tool | 없음 | 없음 |
| Tool 호출 수 | 0 | 0 |
| 입력 토큰 | 491 | 7,225 |
| 출력 토큰 | 113 | 108 |
| 전체 토큰 | 604 | 7,333 |
| 실행 시간 | 1.4초 | 1.5초 |
| 정답 확인 | 통과 | 통과 |
| 품질 점수 (LLM-judge) | 5 | 5 |

**Minimal이 더 낫다고 본 이유**: 두 mode 모두 도구 없이 바로 답했고 출력 길이도 거의 같다. 차이는 입력 토큰뿐인데, Standard는 질문 한 줄을 보내려고 시스템 프롬프트와 도구 설명을 7천 토큰 넘게 함께 보냈다. 간단한 계산 질문에서 이 기본 비용은 답의 질을 높이지 못한 채 토큰만 12배로 늘렸다.

## 3. 나머지 후보까지 포함한 전체 결과

| 질문 | Minimal 전체 토큰 | Standard 전체 토큰 | Minimal 시간 | Standard 시간 | Minimal 정답 | Standard 정답 |
|---|---:|---:|---:|---:|---|---|
| 3의 배수 합 | 604 | 7,333 | 1.4초 | 1.5초 | 통과 | 통과 |
| 요일 | 664 | 15,178 | 1.5초 | 3.3초 | 통과 | 통과 |
| 화씨 → 섭씨 | 535 | 7,234 | 0.9초 | 1.1초 | 통과 | 통과 |
| 존댓말로 바꾸기 | 840 | 7,424 | 2.5초 | 2.1초 | (judge 5) | (judge 5) |
| TCP와 UDP 세 줄 설명 | 777 | 7,354 | 2.5초 | 1.7초 | (judge 5) | (judge 5) |
| JSON 문법 고치기 | 686 | 7,334 | 1.6초 | 1.5초 | 통과 | 통과 |
| .txt 파일 세기 | 1,314 | 14,783 | 2.3초 | 2.5초 | 통과 | 통과 |

일곱 질문 모두 두 mode의 정답이나 judge 점수가 같았고, 전체 토큰은 Minimal이 89~96% 적었다. 다만 "더 잘 답했다"고 말하기 어려운 질문도 있다. 존댓말 바꾸기에서 Minimal은 "늦지 마세요"라고 썼고 Standard는 "늦지 않도록 해 주세요"라고 써서 Standard 쪽이 더 공손하다. 실행 시간도 TCP/UDP 설명, 존댓말 바꾸기, JSON 고치기에서는 Standard가 조금 더 빨랐다.

그래서 위 3개는 정답이 분명해서 품질 차이가 없다고 말할 수 있고, 토큰 차이가 크게 난 질문으로 골랐다.

### 참고: 같은 구성을 LangChain/deepagents로 다시 만든 엔진

DeepSeek Harness 결과가 하네스 구현 탓인지 구성 탓인지 확인하려고, 같은 프롬프트와 도구 구성을 LangChain으로 재현해 같은 질문을 돌렸다.

| 질문 | Minimal 전체 토큰 | Standard 전체 토큰 | Minimal 시간 | Standard 시간 |
|---|---:|---:|---:|---:|
| 서울 날씨 | 8,956 | 21,444 | 19.8초 | 8.4초 |
| 3의 배수 합 | 632 | 7,323 | 1.4초 | 1.5초 |
| 요일 | 751 | 7,482 | 2.0초 | 1.9초 |
| 화씨 → 섭씨 | 544 | 7,193 | 1.3초 | 0.9초 |
| 존댓말로 바꾸기 | 1,072 | 7,333 | 3.8초 | 1.3초 |
| TCP와 UDP 세 줄 설명 | 735 | 7,356 | 2.4초 | 2.1초 |
| JSON 문법 고치기 | 709 | 7,279 | 1.8초 | 1.3초 |
| .txt 파일 세기 | 1,306 | 22,566 | 2.4초 | 3.2초 |

두 엔진 모두 도구 없이 답한 다섯 질문(3의 배수 합, 화씨, 존댓말, TCP/UDP, JSON)에서는 Standard가 7,200~7,400 토큰, Minimal이 500~1,100 토큰으로 DeepSeek Harness와 거의 같게 나왔다. Standard의 기본 비용은 특정 하네스 구현이 아니라 Skill과 도구를 많이 실은 구성 자체에서 온다는 뜻이다. 도구를 쓴 질문은 엔진마다 호출 횟수가 달라서 숫자도 달랐다.

서울 날씨의 Minimal은 처음 실행에서 317초가 걸렸다. 모델 문제가 아니라 LangChain `ShellToolMiddleware`의 버그였다. `curl ... | head -c 2000`처럼 출력이 줄바꿈 없이 끝나면 명령이 끝났다는 신호를 놓쳐서 300초 제한까지 기다렸다. 이 버그를 고친 뒤 다시 돌린 값(19.8초)을 표에 적었다. 같은 명령을 쓴 DeepSeek Harness 실행에서는 이 문제가 나타나지 않았다.

## 4. 정리

필요한 기능만 둔 구성이 대부분의 질문에서 더 효율적이었다. Standard는 질문 하나를 보낼 때마다 시스템 프롬프트와 도구 설명으로 7천 토큰 남짓을 먼저 깔고 시작한다. 도구를 한 번 부를 때마다 이 비용이 다시 붙는다. 정답이 정해진 짧은 질문에서는 이 비용이 답의 질로 돌아오지 않았고, 요일 질문처럼 쓸 필요 없는 도구를 부르게 만들기도 했다.

반대로 최신 정보가 필요한 질문에서는 Skill과 도구가 많은 쪽이 나았다. 서울 날씨에서 Standard는 검색 도구로 기사를 읽어서 더 빨리, 더 많은 맥락을 담아 답했다. Minimal은 bash 하나로 날씨 API를 직접 골라 불러야 했다.

그래서 "Skill은 많을수록 좋은가"에 대한 이번 실험의 답은 "질문에 따라 다르다"이다. 도구가 필요 없는 질문이 대부분인 환경이라면 기본 구성은 가볍게 두고, 검색처럼 꼭 필요한 기능만 필요할 때 붙이는 편이 낫다.

한계도 있다. 각 조합을 한 번씩만 실행해서 실행 시간의 편차는 확인하지 못했다. 토큰 차이는 프롬프트 구성에서 오는 몫이 커서 크게 흔들리지 않겠지만, 1초 안팎의 시간 차이는 반복 실행으로 다시 확인해야 한다.
